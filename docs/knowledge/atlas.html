总览与依赖

UmbraFlow 根据视觉证据授权严格后台点击：平台无关模块负责识别与授权，Windows 代码负责捕获与投递，两者只在 entry/ 组合。下图箭头表示「依赖于」，越靠下越基础。本页由脚本从源码抽取生成，每个类型的 file:line 都可点击，在 VS Code 中直接打开对应位置。

modules/core — 平台无关能力内核

core 是模块图最底部的平台无关叶节点：它只提供可移植、可审计、能消除一类无效状态的小机制（错误表示、受检运算、强类型词汇、同步访问、作用域清理等）。

modules/domain — 领域类型

domain 是 UmbraFlow 的平台无关语义层，把“哪一帧、哪个目标实例、哪个坐标系、这次动作是否仍可信”编码成可跨模块传递的不可变值。

23 个类型

modules/vision + modules/image — 视觉与图像

两个平台无关的小型模块，编辑器、预览与运行时都会用到但彼此不依赖。

13 个类型

modules/annotation — 标注与授权

annotation 把作者在源截图上画的标注编译成内容寻址的运行时识别清单，并用同一套有界灰度 SAD 路径在运行时把页面锚点收敛为 ResolvedPage / UnknownPage / AmbiguousPages。

61 个类型

modules/engine — 运行时编排

engine 是产品运行时的编排层：把已发布的标注项目变成可执行的识别运行时，从已绑定目标的帧源取帧，在同一帧上解析页面与动作目标，调用 annotation 的授权策略，最后把已授权的 client-space 点击交给输入端口。

14 个类型

modules/controller — Windows 桌面能力适配层

modules/controller 把窗口枚举、目标解析与代际、WGC 屏幕捕获、严格后台输入投递、进程 DPI 前提这五组 Win32/COM/D3D11 能力，收敛成 core 的 Result/Status 与 domain 的 Frame/坐标值。

36 个类型

modules/script — Luau 任务 VM 与安全边界

modules/script 为每个任务 generation 创建并独占一个 Luau VM，提供同步源码执行、沙箱、记账内存配额和不可吞的 interrupt 取消。

11 个类型

entry/cli — 产品命令行、task 启动与 Windows 组合根

entry/cli 是 umbra-flow 的命令行入口，也是 Windows 上把平台无关 engine 端口接到真实捕获与后台输入的组合根。

12 个类型

entry/workbench — 标注工作台

umbra-workbench 是 Windows 标注工具，把 annotation、image、vision、controller 组合成 page-centric 作者工作台。

modules/core — 平台无关能力内核

32 个类型

core 是模块图最底部的平台无关叶节点：它只提供可移植、可审计、能消除一类无效状态的小机制（错误表示、受检运算、强类型词汇、同步访问、作用域清理等）。所有其他模块可以依赖它，它不依赖任何项目模块，出边只有 C++23 标准库。它不含产品语义，只给出无歧义的表示与检查，具体失败策略由业务 owner 模块决定。

不负责什么
  • 不定义产品语义（frame、detection、annotation、engine session、Windows handle、Luau、GUI、具体游戏），也不决定失败该 retry、abort 还是展示。
  • 不接触窗口、capture API 或输入投递，无法判断动作是否落到背景目标；strict-background 由 controller 与组合根执行。
  • 不复制标准库：Result 是 std::expected 的 alias，缺席仍用 std::optional，所有权仍用标准智能指针与值类型。
  • 不含 serialization、VFS、job system、task runtime、channel、profiling、intrusive references 或自制容器。
  • 错误分类的产品词汇（std::error_category 与 classifier）留在 owner 模块，core 不内建产品 enum。
  • 不依赖任何项目模块，也没有聚合 core.hpp；调用方必须精确 include 所需 facility。

  1. docs/knowledge/cn/module-core.md先建立模块职责与不该做什么的边界，再对照代码（文档可能滞后，以代码为准）。
  2. modules/core/source/core/error/error.hppError 是贯穿全仓的 move-only 失败表示，理解它才能读懂其他接口的返回类型。
  3. modules/core/source/core/error/result.hppResult/Status/fail 与 UF_TRY 系列宏定义了整个仓库的错误传播语法。
  4. modules/core/source/core/error/contracts.hpp不可恢复的 programmer defect 走终止通道，与可恢复 Error 是两条正交路径。
  5. modules/core/source/core/types/strong-value.hppStrongValue 是 StrongId、Generation 等互不混淆词汇的基座。
  6. modules/core/source/core/numeric/checked-arithmetic.hpp先证明运算有效再执行，是 core fail-closed 范式最典型的示例。

23 个类型

domain 是 UmbraFlow 的平台无关语义层，把“哪一帧、哪个目标实例、哪个坐标系、这次动作是否仍可信”编码成可跨模块传递的不可变值。它只依赖 core，被 vision、image、annotation、engine、controller 和 script 共用。它提供坐标空间与几何、强类型身份、帧与像素所有权、动作时效凭证和自动化错误分类，本身不做识别、窗口管理或输入投递。

不负责什么
  • 不产生 CaptureSessionId / FrameId：CaptureSessionId 由组合根（CLI）提供，FrameId 由 controller 的 FrameIdCounter 逐捕获分配。
  • 不判断目标何时换代：controller 的 ResolvedTarget 根据进程实例、句柄、client size 推进 TargetGeneration。
  • 不解释检测标签能否触发动作：annotation 的授权才绑定 catalog、recognizer、page 与 live fingerprint。
  • 不执行模板匹配、裁图、PNG 编解码、trace 或重试——分别属于 vision、image、engine 或调用者。
  • 不实现 strict-background：后台投递由 controller 的 PostMessageW 边界完成，禁止前台化 API。
  • 不给 Point/Rect/Detection 构造器附加隐式校验；安全边界必须显式调用 create/ensure/授权函数。

modules/engine — 运行时编排

14 个类型

engine 是产品运行时的编排层：把已发布的标注项目变成可执行的识别运行时，从已绑定目标的帧源取帧，在同一帧上解析页面与动作目标，调用 annotation 的授权策略，最后把已授权的 client-space 点击交给输入端口。它只依赖 core/domain/annotation，通过几个窄端口与平台解耦，因而识别与授权可在没有桌面、没有 HWND 的 CI 中复现。

不负责什么
  • 不发现窗口、不创建 WGC、不调用 Win32 输入 API（无 controller 依赖）。
  • 不决定具体平台如何严格后台投递，只通过 IActionSink 写下契约。
  • 不拥有目标选择、DPI awareness、窗口 geometry 或 Ctrl-C 注册，这些在 entry/cli。
  • 不编辑或发布 annotation 项目，只读 generated/annotations.runtime.toml 与其闭包内模板。
  • 不实现 Luau 宿主、任务队列、pause/resume 或常驻进程生命周期。
  • 不定义 trace 文件存储策略：serializer 不做 I/O，也不追加换行。

modules/controller 把窗口枚举、目标解析与代际、WGC 屏幕捕获、严格后台输入投递、进程 DPI 前提这五组 Win32/COM/D3D11 能力，收敛成 core 的 Result/Status 与 domain 的 Frame/坐标值。它是产品与 Windows 之间唯一的平台边界：所有 HWND、COM、驱动生命周期集中在 platform/ 目录，向上只暴露值与结构化错误。公开类型在 uf，纯逻辑在 uf::controller_detail，Win32 桥在 uf::controller_platform。

不负责什么
  • 不识别页面、不解释 Detection、不授权动作——这些属于 annotation 与 engine。
  • 不决定标题模糊匹配、隐藏窗口取舍或歧义展示策略；只提供精确 selector 与必须唯一的解析。

  • 不校验 ProjectFingerprint，不在 TargetIdentity/DeliveryTarget 里携带 DPI 或 compatibility proof。
  • 不提供前台激活、全局输入或移动真实光标的降级路径；目标不接受 PostMessageW 时直接失败。
  • 不抽象第二个平台，故意保持 Windows-only；跨平台端口在 engine 一侧。

modules/script 为每个任务 generation 创建并独占一个 Luau VM，提供同步源码执行、沙箱、记账内存配额和不可吞的 interrupt 取消。公开头文件只暴露 Engine、EngineConfig 与 opaque lua_State installer seam；Luau C API、allocator、sandbox 和 interrupt 都留在 ffi/ 边界。entry/cli 通过 modules/task 安装 umbra.* capability tables 后使用它，测试 seam 则直接验证冻结、配额和取消证据。

不负责什么
  • 不拥有 observation、page resolution、recognition、action 或 lease；modules/task 通过 HostTableInstaller 注入窄 capability。
  • 不拥有 Windows capture/input，也不绕过 engine/controller 的 strict-background 与授权门。
