# Build and release inside the source tree

Date: 2026-08-20
Scope: `umbraflow-cpp` plus the project template and consumer projects
Status: **proposal** — evaluation of relaxing the project kit's separate-directory
constraint; not yet a ruling.

## Background

A consumer asked why `project build` output and `project freeze` releases live
outside the project repository (a sibling `<repo>-work/` directory) instead of
a gitignored `build/` inside it, the way a C++ project keeps its build tree.
The kit today rejects either directory containing the other:

```text
project source and build directories must be separate:
source="...", build="..."
```

`validateDirectories` in `modules/project/source/project/project-kit.cpp`
rejects `isWithinOrEqual(build, source) || isWithinOrEqual(source, build)`.

## Why the constraint exists

`project build` must leave the source tree unchanged, and the source tree is a
byte-pinned input. But the pin domain is **not the whole tree**: it is the
explicit set of declared files
(`readDeclaredProjectFiles` in
`modules/deployment/source/deployment/project-directory.cpp` reads exactly the
seven single-path members of a deployment plus every
`journal_payload_schemas` entry, one file per declared path). No directory
scan, no plugin path, no artifact blob, no generated artifact enters the pin
domain. The "source is pure input" property therefore does **not** depend on
where the build directory physically sits; a build tree inside the source can
never leak into the hash set, because the hash set is a fixed declared list.

## The relaxation

Allow `build` inside `source` (the common C++ shape); keep rejecting `source`
inside `build` (a build directory containing the source has no use).

Minimal change list:

1. `validateDirectories`: drop `isWithinOrEqual(build, source)`, keep
   `isWithinOrEqual(source, build)`.
2. Tests: the "source tree unchanged" assertion compares a full recursive
   listing; it must compare the declared files' digests instead (the kit's
   own `check` already compares exactly those). Other tests assuming an
   outside build get the same sweep.
3. Template downloader: `work_directory()` defaults to `<source>/build` and
   `<source>/release`.
4. Template `.gitignore`: gain `build/`, `release/`.
5. Public contract §3 and the template README restate the directory
   relationship and the refusal text.

`check` semantics do not change: it compares recorded digests against the
declared files read through the loader, never a directory scan. The
three-layer output topology (declared input / generated output / immutable
snapshot) does not change; only the location of the output roots moves inside
the repository.

## Cost

- A misconfigured ignore could commit generated bytes into the repository;
  the same convention every C++ project already relies on. The pin domain
  itself is unaffected by construction.
- Contract surface text changes (refusal wording, template flow).
- No new guard is needed: a declared input pointing under `build/` would be a
  wrong path the existing declared-file comparison already refuses at check.

## Benefit

- A self-contained project repository with gitignored `build/` and
  `release/`, portable and CI friendly, with no sibling-work directory to
  explain.
- Removes the one remaining "why is this outside?" friction in the template
  flow.

## Recommendation

**Approve the relaxation.** The pin domain is a fixed declared file set, so
the structural guarantee the separate-directory rule appeared to provide is
already enforced by the pin domain itself, not by directory topology. The
change is small, testable, and the consumer's existing sibling `-work/`
layout stays valid (only the template default moves).
