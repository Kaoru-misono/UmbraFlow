# Shared RFC 8785 (JSON Canonicalization Scheme) test vectors.
#
# RFC 8785 is spelled three times in this repository -- core/text/json-text.cpp
# in C++, tools/annotate/jcs.py in Python and modules/task/runtime/jcs.luau in
# Luau -- and bytes produced by one are hashed and verified by another. A
# divergence between two spellings cannot fail either one's own tests; it
# produces bytes that merely disagree. These rows are the one place all three
# are held to the same expectations.
#
# Expected bytes come from V8, which is the reference RFC 8785 itself cites:
# JSON.stringify IS the required string form, String(n) IS Number::toString and
# JS < on strings IS UTF-16 code-unit order. They are NOT derived from any
# implementation under test.
#
# CONSUMERS
#   tests/core/test-json-text.cpp         reads this file
#   tools/annotate/tests/test_backend.py  reads this file
#   tests/task/test-jcs.luau              embeds the rows verbatim, because the
#                                         Luau sandbox cannot open a file;
#                                         test_backend.py fails when the
#                                         embedded copy and this file disagree.
#
# FORMAT
#   Blank lines and lines starting with # are ignored.
#   `count <N>` appears exactly once and states how many rows follow. A
#   consumer that parses a different number must fail: a vector file that
#   failed to load would otherwise turn every assertion here into a silent pass.
#   A row is space-separated tokens. A token containing = is an outcome
#   override, a token equal to # ends the row and starts a human label, and
#   everything else is a positional field.
#   Every field is x followed by lowercase hex of raw bytes, so the empty
#   byte string is a bare x, or - when the field does not apply. Hex keeps this
#   file pure printable ASCII containing neither a quote nor a backslash, which
#   is what lets the Luau test embed the rows as plain string literals.
#
# OUTCOMES
#   Each row states one expectation per implementation. With no override an
#   implementation must produce the row's expected bytes exactly. An override is
#   cpp=, py= or luau= followed by one of:
#     reject  the implementation must refuse this input, by its own error
#     absent  the implementation has no entry point for this rule at all
#     x<hex>  the implementation produces these bytes instead
#   A row whose expected field is - asserts nothing through that field, so every
#   implementation that reads it must carry an override: py and luau always, and
#   cpp for every kind except order, where cpp reads the name list instead.
#
# ROW KINDS
#   string <input> <expected>
#       <input> is the raw bytes of a JSON string value; <expected> is the
#       complete canonical string token, surrounding quotes included.
#   order <expected> <name>...
#       The member names in canonical order. C++ has no value-tree encoder, so
#       it checks the name sequence with its ordering predicate and ignores
#       <expected>; Python and Luau build an object mapping each name to its
#       1-based canonical position and must emit exactly <expected>.
#   integer <literal> <expected>
#       <literal> is an exact decimal integer in ASCII. Python reads it as an
#       arbitrary-precision int; Luau reads it as a double, which may round it
#       before the encoder ever sees it.
#   empty-object, empty-array
#       The empty container of that shape, which carries no field but its
#       expected bytes. Lua has one empty table for both, so this is the one
#       value the three cannot all spell the same way.
#   double <literal> <expected>
#       <literal> is ASCII: either a decimal literal, or one of the four names
#       nan, inf, -inf and -0, which each consumer maps rather than parses so
#       that no strtod detail gets to decide the sign of a zero.
